- Sticky mobile bar matches the site's own styling (no floating white pill), is mobile-only, and hides over the hero (hero has its own CTAs), forms and footer.

NEVER run wrangler deploy against another site's worker name (this overwrote the shared starter demo once). Check `wrangler.jsonc name` before every deploy; restore an overwritten worker with `wrangler rollback <version-id>` and verify the title.

Do not turn one unavailable stock API into a request for the operator to solve a routine sourcing task. An image-API call only ever runs after an explicit operator GO for that exact need. When he supplies a logo sheet, IT is the image source of truth for logos/favicons AND stylesheet tokens (sample its exact hexes, restyle theme tokens, keep palette/a11y audits green). No AI logo ever — the operator designs logos himself; use a wordmark treatment.
- MAPS ARE NEVER PICTURES (D-148): a map slot uses an EMBEDDED Google map (business listing, timed/locations, or main location). A static map image in a map slot is a build failure — a builder defaulting to a map screenshot means the brief did not restate the law. The map iframe AUTO-LOADS on page render, full-width per the template's areas treatment — no click-to-load facade, no image placeholder in front of the embed (operator override 13 Oct: 'it should automatically show'); the click-to-load performance pattern is not wanted on these sites.
- TEMPLATE DESIGN-TOKEN EXTRACTION IS MANDATORY in every capture (D-148): pull the template's radii (rounded buttons/cards), shadows, spacing scale and font treatment from its CSS into the site's token files, then build against those tokens. 'Buttons not rounded like the template' = fidelity failure. Extracted tokens get operator overrides applied (e.g. a yellow/black scheme replaces the template palette only on his explicit word), and contrast pairs are declared per token (fg/bg/min-ratio) so WCAG AA is checkable.
- COLOUR CONTRAST IS A BUILD FAILURE (D-149): grey-on-grey or any text/background pair below WCAG AA (4.5:1 body, 3:1 large) never ships — verified per element in the QA walk, not assumed. A contrast fail reaching the operator means the fix-until-pass loop was not run honestly.

Always background+notify. Full-loop 'done' stays the bar for page rebuilds and new page types.

## SERVER HYGIENE DURING BUILDS (hard lessons — the box OOM-killed a gateway mid-chain)
- Before scheduling parallel builds, measure `free -h` (especially available memory, not just free), swap, disk, active build processes and orphaned preview servers. Allow independent site builds concurrently when measured headroom supports them; do not turn an earlier OOM event into a permanent one-build limit. Browser QA can spike after coding has been quiet: sample memory while BOTH build and browser checks run, not just at dispatch. If OOM occurs, use `journalctl -k --since ...` to identify the killed process and swap/free state at the event; do not infer that the killed process alone consumed the missing gigabytes. Reduce concurrency only on observed pressure, preserve partial edits, and alert the operator immediately. Never run two builders in the same checkout.
- Every CC/Codex session STOPS its dev/preview server and workerd when done — orphaned preview
  servers sat at 1.3GB for hours ('why is the server starved'). Before declaring a session done,
  `pgrep -f 'astro dev|workerd'` and kill what the session started (by PID).
- Desk-clearing is routine, not exceptional: npm/pip/pnpm caches and dead node_modules in test
  dirs grow to 10GB+ silently. Prune when disk >80% (`df -h /`): `npm cache clean --force`,
  `rm -rf /root/.cache/{pip,huggingface,pnpm}`, dead test trees' node_modules. Keep
  ms-playwright cache (browser QA needs it).
- Kill stale processes by verified PID only (see kill-law above). Gateway/systemd OOM evidence
  lives in `journalctl -u hermes-gateway -S <time>` — check it when a chain dies without a
  stage-exit line before blaming the builder.

## Factory dependency and build-location boundary

For SiteBuilder v4 factory improvements, distinguish the factory rules/gates repository from the separate Astro starter repository. Start by inspecting the starter's actual branch, manifest, route components and tests; a factory specification or `not-built` pin does not prove the starter exists or works. Develop each on an isolated branch/worktree, preserving `main` as rollback. Keep client identity, claims, photographs and research paths out of a distributable starter; `site.config.ts` owns approved business/NAP/services/towns/design tokens, while porting a supplied template may still require editing layout/components. A named template controls visual layout; Way Valley is a fallback only when no template is supplied. If neutralising a copied client seed, preserve the fallback's structural composition and styling without transplanting restricted client assets, and test that named-template mode cannot silently use fallback sections or CSS.

Draft Astro/Tailwind CSS v4/Cloudflare manifests in source control without installing packages on the Hermes orchestration server; call them pinned and compatible only after exact versions, lockfile and an isolated client-repo/CI build prove the combination. A source-only manifest is not a working starter. A new site gets its own GitHub repository; package installation/build belongs in that site's isolated environment or CI, and output deploys to its own Cloudflare Worker. Do not mistake a factory source edit for commissioning a new site or trigger CI just to mask the build-evidence gap. Before any server-side install, the explicit RAM/disk approval law still applies. Review starter changes against the actual base diff, run safe source-level tests, and independently inspect readiness gates, route/config wiring, form-error UX, provenance, worker-name uniqueness and any retained client-specific strings. Exercise native POST errors across the site endpoint AND upstream form worker (validation, rate limit, unavailable storage and delivery): translating local validation into accessible HTML is insufficient when an upstream JSON error is forwarded unchanged to a no-JS visitor. Require mutation tests for omitted mandatory routes/sections, incomplete named-template page maps and required sections that render empty or generic placeholders: a route list or declared content schema without functional rendered coverage is not proof. Keep source-only readiness BLOCKED until an authorised isolated build and served-site checks pass; only then update the factory's starter pin. Report source checks, build compatibility, deployment and visual fidelity as separate states. For publication preflight, bind QA and publication to one immutable candidate-input manifest: exclude generated QA/preflight reports and operational writes from that identity, carry selected evidence/waivers/registry inputs explicitly, and test that two runs on unchanged inputs yield the same identity. Otherwise the first report invalidates the second run's QA match. A locally matching receipt is consistency evidence, not authenticated operator approval, source provenance or remote D1 read-back; retain NOT_RUN where the trusted boundary is absent. Follow references/candidate-evidence-boundary.md when implementing or reviewing the capture, QA, preflight and D1 read-back path. When that reference is not enough for the current defect, stop patching and write a read-only method-level diagnosis brief first: require the diagnosing session to reproduce each reported finding with an in-memory probe against the real code paths, propose a total typed model (not another selector), and name exact files — then implement from that diagnosis, not from the review alone. When a shared infrastructure account (Codex/Claude Code subscription) exhausts mid-project, the approved fallback is handing continuation to the other builder with a written checkpoint brief; batch that builder's work as implementer → orchestrator verification (focused tests, one light suite, generator/repo/diff checks) → fresh staged-diff reviewer → repair P0/P1 → commit, one batch at a time, and have subagent reports returned as final text (subagents cannot write report files in that harness; save them from the transcript yourself). Never foreground a long `claude -p` run even for reviews — the terminal cap kills it mid-review; launch background+notify from the first attempt, and after a blocked or failed launch, change the launch pattern rather than retrying the identical command. After every launch, verify the builder's child process is actually alive (pgrep for the builder binary) and the worktree is untouched-but-clean as expected before reporting it running to the operator — a launch killed by the tool timeout (exit 124) left nothing running, and reporting a killed launch as 'running' is a false status the operator acts on. A CI workflow file in the starter repo exists to prove the Astro stack compiles in GitHub's environment WITHOUT any install on the Hermes box — pushing the starter branch and letting that workflow run is the sanctioned starter-build proof (operator-approved path); triggering it is not a masked install, and the starter pin updates only after the CI build and served-site checks pass. A workflow with only `workflow_dispatch` on a non-default branch is NOT runnable: GitHub does not register dispatch-only workflows absent from the default branch (API dispatch returns 404), and a push trigger fires only for the branch filter the file declares. Before promising CI proof, verify the trigger type + branch filters in the workflow file, confirm the workflow is registered (workflows API lists it), and confirm an exact dependency pin + lockfile exist (a floating `astro` dependency makes install nondeterministic); generate lockfiles off-server per the no-install law.

PILOT COMMISSION INTAKE (new-site commission through the v4 factory): before composing any inventory or site-plan.json, resolve the client EXACTLY as the operator names it — grep the brain's build-state file AND the planner sites/ list for the spoken name and domain; several lookalike trade clients coexist and the local planner checkout may be BEHIND origin (an operator-approved plan committed remotely is invisible until `git fetch` + read from origin). If the named client has no plan, stop and tell the operator a plan must be created first (real NAP, services, towns, monetisation); never substitute a lookalike plan. Check the seed NAP block for placeholders: the business NAME must be real before build (identity, not a slot), but phone/address placeholders do NOT gate the build — render clearly-marked placeholder values (e.g. '0000 000 0000', 'PLACEHOLDER ADDRESS') so the later swap is a trivial content edit; record the swap as a pending content task, never invent or source values from wayback/ledger contact rows. Blocking a build for phone/address reads as stalling to the operator — his ruling is build first, supply the rest afterwards. Check zone/DNS status read-only (a parked zone with 0 DNS records cannot serve; note any existing worker routes on the zone for go-live review). Set up the project root under lead-gen-websites/<domain>/ and move any already-captured template reference-library there unchanged (verify checksums after the move); compose the v4 site-plan.json by merging the approved seed with the factory standard-inventory registry, validate against the factory schema with `python3 -B`, and record every seed/registry conflict in PLAN-CONFLICTS.md rather than silently resolving. For operator 'which template does variant X use' questions, the binding template URLs live in the site's per-variant *-BRIEF*.md files at the site repo root — grep those first; plan/seed files carry content, not looks.

## Full-build dispatch (start-to-finish runs)
- For a new build, start with the approved site plan and named template (if supplied), then merge the separate standard-page registry into a single explicit route inventory with positive and negative requirements. Use the starter as a pinned, tested technical framework with current compatible dependencies, not a visual template to edit or recolour. Do not silently upgrade dependencies mid-project. If Vince names a template, capture its CSS/markup and use its visual layout as the base; add required section *types* (reviews, gallery, forms) using the named template's visual language, never the Way Valley fallback component appearance. If no template is supplied, use the fallback visual recipes. In either case the starter supplies Astro/Cloudflare plumbing and reusable behaviour, not a design to clone and recolour. Keep the page registry outside the starter so a component's presence never decides whether a page exists. Stage a self-contained root brief with source URL, capture step, seed, applicable rule checklist, worker name, live-domain path, media provenance and prohibited copy. Verify the starter actually exists and is pinned before invoking it; a wireframe renderer is not a releasable starter.
- A builder session completes its BRIEF, not the operator's goal — brief it to 'fix build errors' and it fixes build errors and honestly reports it did not do the design. Write the real acceptance bar INTO the brief (e.g. 'the DEPLOYED site visibly matches the named template, verified against the capture'), never intermediate gates ('build compiles', 'structure verified') — sessions stop at their brief's edge, so the brief must end at the operator's bar.
- DEPLOYMENT IS A BUILD STEP (operator law): a build is not finished until it is deployed and viewable — every build session deploys its output to a worker URL (workers.dev preview route when the client zone is not live) and its report carries the URL plus read-back status codes. Never report 'built' without a viewable URL; a build-without-deploy reads as no work done.
- FULL PAGE FURNITURE (operator law): a build delivers every page COMPLETE, never a route skeleton — each page carries the template's full treatment: page hero with the template heading style AND both hero CTAs, services grid with card images, areas section with a live map embed (D-148), quote-form/CTA band, FAQ accordions where planned, gallery (ALWAYS — operator law: the gallery is a standard site-builder component on every build, never 'where planned'), template footer, sticky mobile bar. The GALLERY, mid-page CTA BAND (every page) and OUR-WORK showcase section (home) are STANDARD COMPONENTS: they must exist in the starter/factory code so every build inherits them mechanically — a one-off patch on the current client build is not compliance. The map embed is FULL-WIDTH per the template's areas treatment. A near-empty page is a failed page: verify EVERY route's rendered furniture on the deployed URL, per route — checking only `/` and one sample page hides a whole class of empty-page failures.
- ICON SET SHIPS IN EVERY REPO (operator law): favicon.ico, favicon.svg, 16/32 PNGs, apple-touch-icon, 192/512 icons plus their <head> links live in public/ — a missing favicon is a missing build step, and builders skip it unless the brief restates it. Port the named template's captured icon set (own-fleet asset) until the client's own logo/icons exist; the operator designs logos himself.
- CONVERSION-FIRST COPY LAW: headings/H1s lead with the customer problem then the answer ('Struggling to find a reliable plasterer in Bradford? ...'), never bare keyword headings ('Plasterer in Bradford') that don't convert; marketing copy quality is a build deliverable, not post-launch polish. The no-fabrication law bans invented FACTS (stats, reviews, credentials, claims) — it does NOT ban honest service description: a shipped page with empty body copy is the failure mode, and truthful description of an approved service is the fix. Never let a builder over-apply no-fabrication into empty pages.
- RULE TRANSPORT LAW (operator-approved structural fix): embed the FULL law set into the starter repo as `CLAUDE.md` + `.claude/rules/*.md` — Claude Code auto-loads them every session, so rules stop depending on Zeus restating them in briefs (brief summaries are where rules get dropped: a founding Quick Quote CTA law shipped wrong because no brief carried it verbatim). Pair with a BUILD COMPLETENESS GATE in the starter: a check over mandatory furniture (quote form section, Quick Quote hero CTA, gallery, real map embed, favicon refs, service body copy). GATE SEMANTICS (operator clarification 13 Oct): AUTO-REPAIR LOOP, never a silent fail — when the gate finds something missing, the builder ADDS it per the defaults (form renders, gallery populates from our captured assets, map becomes a real embed, CTA becomes Quick Quote, truthful copy written) and rebuilds until the gate passes. Stop-and-ask ONLY for what genuinely needs operator input (real NAP, MJHQ connector declaration, real reviews), and even then ship the placeholder version and list the swap — never drop the section, never ship without it. Structure-only gates ('astro check: 0 errors') pass sites missing entire sections; only a completeness gate with auto-repair makes that unshippable.
- HERO CTA RULES: the home hero's primary CTA is ALWAYS 'Quick Quote Online' → the quote form — never an 'Our services' link as the primary hero CTA (services links belong in nav/body). The HEADER phone button renders ONLY a real business number: placeholder NAP never renders as a header phone button (omit the slot entirely); footer/contact sections keep placeholder NAP as plain text per the placeholder policy.
- PLACEHOLDER POLICY: missing data (real NAP, reviews, connector declarations) NEVER drops or gates a section or the build — render clearly-marked placeholder slots and record the swap as a pending content task. Blocking a build on data the operator said he will supply later reads as stalling.
- Use templates/chain-build.sh for dependent stages of ONE site; finish the prior stage before starting the next stage in that checkout. Independent sites may build concurrently after the resource check above. Do NOT generate article pages or schedule an articles stage by default; add one only when explicitly commissioned in the approved plan — but when the plan DOES commission a count (e.g. articleCap: 3), those articles are a build deliverable, not optional polish: render them as real article pages in the named template's own captured article treatment (its structure, density and image handling), wired into routes/sitemap/nav. Hub/category pages are not a pretext to generate child pages.
- Operator timing tests: every brief orders a TIMING.md with per-phase wall-clock durations, and the chain log timestamps every stage start/exit. When asked how long a site has taken, read its timing log AND live clock with a tool; give the earliest verifiable build start, current local time in the operator's timezone, elapsed wall-clock time per site, and the still-unaccepted stage. Separately label active agent runtime, idle/stalled intervals, and overlapping time across parallel sites; never add parallel runtimes and present the sum as elapsed calendar time. If the question includes planning or preparation before the logged build, distinguish that unknown/earlier start rather than guessing. Verify git/deploy/real-domain state before explaining where the time went; a first build duration is not the delivery duration when correction rounds and release delays follow.
- Audit-only passes (report, no changes): the brief forbids touching anything except the output
  report file, points the auditor at the smoke ruleset (olympus app/smoke-test.js +
  scripts/smoke-test.mjs) and demands per-site numbered work lists in operator order (rev-share first).
- Inventory questions ('what plans are ready/unbuilt/at 100%'): references/site-plan-inventory.md
  — planner state machine invocation + the cross-checks (KNOWN_BUILT, live-title probe, worker
  attachments, domain ownership) before calling anything unused. The planner sites/ list can also
  lag origin/main: `git fetch origin` and read from origin before declaring a plan missing.

Telephony wiring (07 mobile law, see zeus-brain 50-telephony for full spec): before buying a number, LIST the account's existing numbers and the ledger — a spare 07 mobile may already exist (a GB mobile purchase can also fail on a regulatory-bundle requirement). Never reuse a number assigned to another site; 07700-range numbers are Ofcom-reserved drama numbers — unusable for campaigns. Verify a 'spare' against the NUMBER-LEDGER and RingTonic/Twilio friendly names before assigning.

LEAD-GEN DISCLOSURE + BUILD-BRANDING LAW (operator, committed to the repo copy of record):
- Every lead-gen site we market (including rev-share sites built for a client): the FOOTER
  states it is a lead-gen site; the THANK-YOU page says we are a lead-gen site and will put
  the customer in contact with the best person for the job in their area; a REV-SHARE site
  additionally NAMES the partner company and tells the customer to expect a call from that
  company (so the call is never 'who are you?').
- LEAD-GEN BRANDING SPLIT: rev-share/client lead-gen sites (Multiskim, Rigbys, BFL class) carry NO
  Local Map Booster / agency branding anywhere — no 'built by' credit at all. OPERATOR-OWNED
  lead-gen sites (DrainPlumb class) DO carry the keyword-linked build credit in the bottom bar
  ('drainage websites' linking to localmapbooster.com — link on the keyword, never the brand name).
  On any lead-gen site the build credit is `rel="nofollow"` per the link gate unless the
  operator says otherwise.
- MJHQ / My Job Home Quote is NOT wired into the v4 form system until the operator declares
  the connector ready — never wire, claim, or stub MJHQ form delivery before he says so.
- FORM LAW: the quote form RENDERS on every build by default, styled per the named template —
  a form is part of the build, never dropped behind a `capabilities.forms: false` flag. Only
  the SUBMISSION path stays unwired until that site's connector is declared; the form shell,
  fields and button ship in the template's own form treatment. A build that drops the form for
  missing capability data has shipped an incomplete site. The normal form is ALWAYS used first —
  it renders and posts same-origin (`/api/lead` → D1); the MJHQ API connection is a later
  integration layered on top, never a blocker for the form existing.
- REVIEWS LAW (operator ruling, supersedes the honest-empty default): when no real reviews are
  supplied, the builder/model WRITES up to 10 reviews for the reviews section and they ALWAYS
  LOOK REAL — normal customer-review rendering per the template, names/ratings/dates, NO
  visible placeholder marker on the page. Build records still track them as the written set for
  the later swap to real GBP reviews when the operator supplies them. An empty/dashed-outline
  "insert reviews here" state is a failed build, not compliance. The no-invented-FACTS law (stats,
  credentials, claims) stands; review quotes are the operator-approved exception, and real GBP
  reviews replace the written set wholesale on supply.
- Update-vs-wipe on an existing site is the operator's per-site call: a v3-era build can be
  excellent and kept (maybe colour tweaks only). Present facts, he sorts keep/update/wipe.
